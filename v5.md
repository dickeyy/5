# Quack v5

Quack v5 is an intentional rebuild, not a patch release. It is a platform change from a Discord-first bot to an API-first moderation system with Discord as an execution surface.

## Why v5 exists

### Shortcomings of v4
- v4 treats Discord as both interface and core framework, which tightly couples product behavior to slash commands and message interactions.
- Moderation behavior is too variable between servers, which causes inconsistency for staff and maintenance complexity in code.
- Admins lack strong tools to standardize moderation policy and enforce consistent outcomes.

### Product goals for v5
- Standardize moderation with server-specific case templates.
- Move management workflows to web UI.
- Keep Discord fast for staff execution (`/case add`) instead of full control surface.
- Make automations explicit, auditable, and reliable.
- Keep v4 available as a separate bot for servers that do not migrate.

## Current repository assessment

This repository is no longer just a blank scaffold. It already contains part of the platform foundation, but the moderation domain is still mostly unimplemented.

### Already real
- Process bootstrapping exists in `main.go`: config load, DB connect, Redis connect, migrations, event queue start, Discord connect, API start.
- API server skeleton exists in `api/server.go` with request logging and panic recovery middleware.
- Health/status endpoint exists at `GET /status`.
- Discord OAuth login/session flow exists in `api/routes/auth.go` and `api/middleware/auth.go`.
- Redis-backed auth session persistence exists in `storage/auth.go`.
- A broad v5 schema already exists in `structs/schema.go`, and migrations are wired in `storage/migrations.go`.
- Discord runtime connection exists in `discord/discord.go`.
- Generic async queue infrastructure exists in `services/event-queue.go`.

### Present but still skeletal
- Discord events are only queue stubs (`discord/events/message-create.go`, `discord/events/message-delete.go`).
- The queue is generic infrastructure, not yet the moderation action engine.
- Storage currently exposes almost no domain repositories beyond auth state/session helpers.
- API routes only cover status and auth.
- No application service layer exists for templates, cases, action execution, appeals, tickets, or audit.
- No Discord slash command registration or `/case add` flow exists yet.
- No tests exist yet.

### Important implication
The repo already has enough platform surface to stop scaffolding and start building the first true moderation slice. The next work should not be "more infrastructure for its own sake." The next work should be a thin but complete case-template -> case creation -> action record pipeline.

## Target user flow

1. Moderator sees a violation.
2. Moderator runs `/case add [template] [user]`.
3. API creates the case using the template policy.
4. Action engine executes configured automations (warn/timeout/kick/ban/DM/log/etc).
5. Results are logged in case timeline and audit logs.
6. Admins review and manage everything in web UI.

## Architecture rules

### 1) API-first application core
- API is the source of truth for business logic.
- Discord client is a tool/adapter used by API services.
- Web UI and Discord commands call the same application services.
- No moderation logic should live only in command handlers.

### 2) Domain model that supports policy-driven moderation
Required entities:
- Guild
- Staff member + role mapping
- Case template
- Case
- Case action execution
- Case note/history event
- Appeals
- Tickets
- Audit log

Required template capabilities:
- Standardized reason text.
- Optional severity/weight.
- Escalation rules.
- Action pipeline definition.
- Optional DM rules and message templates.

### 3) Action engine contract
Every action type is a module behind a shared contract.

Minimum initial action set:
- `record_warning`
- `send_dm`
- `timeout_user`
- `kick_user`
- `ban_user`
- `write_mod_log`

Engine requirements:
- Deterministic execution order.
- Per-action success/failure recording.
- Idempotency protection.
- Retry policy for transient failures.
- Safe handling for irreversible actions.

### 4) Discord integration surface
- Keep Discord focused and minimal.
- `/case add` is the primary moderation entrypoint.
- Direct punishment commands are not a foundation priority.

### 5) Web UI boundary
- Web UI is first-class product surface, but it is a separate repository.
- This repository should define clean API contracts first.
- Do not block backend implementation on frontend availability.

## Implementation principles for this repository

### Build one vertical slice at a time
Do not try to implement templates, cases, action execution, Discord commands, tickets, appeals, analytics, and migration at once. Each phase must end in a working path, not another disconnected scaffold.

### Keep the business layer out of routes and Discord handlers
Routes should validate/translate requests. Discord handlers should translate interactions. Real use cases should live in services that both surfaces can call.

### Use the existing schema, but earn the right to extend it
`structs/schema.go` is already broad enough for foundation work. Only extend schema when a concrete implementation step needs it.

### Treat tickets and appeals as later phases
They are already represented in schema, but they should not be the first active subsystem. The first subsystem is template-driven case creation.

### Prefer import tooling over runtime legacy coupling
v4 coexistence should be operational, not architectural. Keep v5 independent and build import/migration tools explicitly.

## Recommended implementation order

### Phase 0: Stabilize the foundation for real feature work
Goal:
- Make the current scaffold safe to build on without changing product scope.

Deliverables:
- Clean up obvious structure issues and naming inconsistencies.
- Ensure route registration, config loading, and service wiring are easy to extend.
- Add the first test harness setup so new domain work can ship with tests.

Concrete work:
- Normalize API route organization around route groups.
- Add test helpers for DB/Redis-backed storage and pure service tests.
- Decide where business use cases live and keep that boundary consistent from the start.

Done when:
- Adding a new API use case does not require inventing architecture again.
- The repo has at least one testable pattern for storage/service code.

### Phase 1: Guild onboarding and RBAC baseline
Goal:
- Turn auth from "identity only" into "guild-scoped authorization foundation."

Why this phase comes first:
- Templates and case creation both require guild context and permission checks.
- Current auth proves identity, but it does not prove who can moderate what.

Deliverables:
- Guild lookup/bootstrap flow.
- Staff member persistence/update flow.
- Guild permission policy evaluation.
- API middleware/helpers for guild-scoped permission checks.

Concrete work:
- Add storage methods for `Guild`, `GuildSettings`, `StaffMember`, and `GuildPermissionPolicy`.
- Add service methods to sync or bootstrap a guild record from Discord context.
- Add permission evaluation helpers using stored guild policy plus permission bits.
- Add minimal protected routes for "who am I in this guild?" and "what permissions do I have?"

Done when:
- A logged-in user can be resolved to a guild-scoped staff context.
- API routes can enforce actions like `case.create` and `case_template.write`.

### Phase 2: Case template management API
Goal:
- Make templates the first real admin-managed moderation primitive.

Deliverables:
- Create/read/update/archive template endpoints.
- Template action definitions and escalation-rule persistence.
- Validation for template shape and action ordering.
- Audit log writes for template changes.

Concrete work:
- Add storage methods for `CaseTemplate`, `CaseTemplateAction`, and `CaseTemplateEscalationRule`.
- Add service-layer validation for slug uniqueness, ordered actions, retry constraints, and escalation rule sanity.
- Add API routes under guild scope for template CRUD and listing.
- Record template mutations in `AuditLogEntry`.

Done when:
- An authenticated guild admin can manage templates entirely through API.
- A template can be fetched in a fully-expanded form ready for case creation.

### Phase 3: First true vertical slice - create a case from a template
Goal:
- Implement the core use case that turns a stored template into a persisted case and queued actions.

This is the first milestone that matters:
- It touches the schema already in place.
- It validates the API-first architecture.
- It becomes the shared contract for Discord and web.

Deliverables:
- `create case` application service.
- Case number allocation per guild.
- Template snapshot persistence.
- Initial case timeline event.
- Action execution rows created in deterministic order.
- Audit log entry for case creation.

Concrete work:
- Add storage methods for `Case`, `CaseEvent`, `CaseActionExecution`, and `AuditLogEntry`.
- Implement transactional case creation:
  - load template
  - evaluate permission
  - apply escalation selection
  - allocate case number
  - snapshot template/actions
  - create case row
  - create initial timeline event
  - create pending action execution rows
  - write audit entry
- Add API route for `POST /guilds/:guildID/cases`.

Scope control for this phase:
- Do not execute the actions yet.
- Do not build appeals/tickets here.
- It is acceptable for the first slice to create pending action records only.

Done when:
- A valid API request can create a case from a template and leave durable pending work for the executor.

### Phase 4: Action execution engine
Goal:
- Turn pending action records into reliable automation execution.

Deliverables:
- Queue-driven execution worker.
- Shared action executor contract.
- Attempt recording and retry behavior.
- Status transitions on case actions and cases.

Concrete work:
- Reuse the existing queue infrastructure, but specialize it around action execution jobs.
- Add service methods to claim pending actions, record attempts, and update retry state.
- Implement the first safe action set:
  - `record_warning`
  - `send_dm`
  - `write_mod_log`
- Add guarded support later for irreversible actions:
  - `timeout_user`
  - `kick_user`
  - `ban_user`

Done when:
- Pending actions can execute in order and record outcomes.
- Failures are visible and retryable where allowed.

### Phase 5: Discord `/case add` integration
Goal:
- Make Discord a real execution surface for the case pipeline, not a separate logic path.

Deliverables:
- Command registration.
- Template autocomplete.
- Guild-scoped permission gate.
- Command handler that calls the same case creation service/API contract as the web/API path.

Concrete work:
- Build command registration in `discord/commands`.
- Add `/case add` with template + user + optional reason override inputs.
- Resolve guild/staff context from Discord interaction.
- Call the shared case creation use case.

Done when:
- A moderator can create a template-driven case from Discord without any moderation logic living only in the command handler.

### Phase 6: Web-facing admin support APIs
Goal:
- Expose the minimum backend surface the separate web repo will need.

Deliverables:
- Template listing/detail endpoints.
- Case search/list/detail endpoints.
- Staff activity summaries.
- Audit log listing.

Concrete work:
- Add paginated filterable APIs for templates, cases, and audits.
- Add case timeline and moderation profile reads.
- Add response shapes stable enough for the separate web repo to consume.

Done when:
- The web repo can build template management and case history views without backend redesign.

### Phase 7: Appeals, tickets, and migration tooling
Goal:
- Add adjacent moderation workflows after the main case pipeline is stable.

Deliverables:
- Appeals API and workflow.
- Tickets API and workflow.
- Import tooling from v4 data where explicitly supported.
- Guild rollout controls and migration markers.

Important constraint:
- This phase should not begin until Phases 1 through 5 are stable enough that moderation itself works end to end.

### Phase 8: Observability, hardening, and release gates
Goal:
- Make v5 safe to run for real guilds.

Deliverables:
- Correlation IDs through API, case creation, and action execution.
- Structured audit/event logging everywhere.
- Metrics around queue depth, action failures, and route latency.
- Integration tests for the critical case path.
- Runbook docs for v4/v5 coexistence.

## What we should build first

The first real implementation target should be:

### First milestone
`guild-scoped template-driven case creation through API, with pending action records but without live action execution`

Why this is the right first milestone:
- It uses the schema that already exists instead of inventing more structure.
- It forces the RBAC model to become real.
- It gives Discord and web a shared contract.
- It keeps scope tight by deferring actual action execution one phase.

What is explicitly out of scope for the first milestone:
- Appeals
- Tickets
- Web UI work in this repo
- Full v4 import
- Full action executor retries
- Direct `/ban` and `/kick` style commands

## Step-by-step backlog we can tackle next

1. Create the service/repository boundary for guilds, staff context, templates, cases, and audit logs.
2. Implement guild-scoped RBAC evaluation on top of the current auth session flow.
3. Implement template CRUD plus validation.
4. Implement transactional case creation from template to pending action records.
5. Add tests around template validation, permission checks, and case creation.
6. Only after that, build the action executor.
7. Only after that, wire `/case add`.

## Definition of done for v5 foundation

Quack v5 foundation is complete when:
- Moderators can execute moderation through `/case add [template]`.
- Templates fully define reason, policy, and automation behavior.
- Action engine executes and records outcomes reliably.
- Admin/staff can manage and review moderation via web UI.
- API is the sole business-logic authority for both web and Discord surfaces.
- v4 can remain active separately without blocking v5 operation.

## Non-goals for foundation scope

- Recreating every v4 command as-is in v5.
- Building advanced customization before the template/action core is stable.
- Mixing v4 and v5 runtime logic in the same command-first architecture.
