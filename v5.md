# Quack v5

Quack v5 is an intentional rebuild, not a patch release. It is a platform change from a Discord-first bot to an API-first moderation system with Discord as an execution surface.

## Why v5 exists

### Shortcomings of v4
- v4 treats Discord as both interface and core framework, which tightly couples product behavior to slash commands and message interactions.
- Moderation behavior is too variable between servers, which causes inconsistency for staff and maintenance complexity in code.
- Admins lack strong tools to standardize moderation policy and enforce consistent outcomes.

### Product goals for v5
- Standardize moderation with server-specific case templates.
- Move management workflows to web UI.
- Keep Discord fast for staff execution (`/case add`) instead of full control surface.
- Make automations explicit, auditable, and reliable.
- Keep v4 available as a separate bot for servers that do not migrate.

## Current state in this repository

The v5 scaffold has started:
- New runtime entrypoint and service bootstrapping exist.
- API server skeleton exists with middleware and health/status route.
- Discord client package exists and is being separated from core app logic.
- DB, Redis, and queue service scaffolding exist.

What this means:
- Direction is correct (API-first).
- Core product systems are still missing (templates, action engine, auth/RBAC, web UI, migration flow).

## Target user flow

1. Moderator sees a violation.
2. Moderator runs `/case add [template] [user]`.
3. API creates the case using the template policy.
4. Action engine executes configured automations (warn/timeout/kick/ban/DM/log/etc).
5. Results are logged in case timeline and audit logs.
6. Admins review and manage everything in web UI.

## Required architecture

### 1) API-first application core
- API is the source of truth for business logic.
- Discord client is a tool/adapter used by API services.
- Web UI and Discord commands call the same application services.
- No moderation logic should live only in command handlers.

### 2) Domain model that supports policy-driven moderation
Required entities:
- Guild
- Staff member + role mapping
- Case template
- Case
- Case action execution
- Case note/history event
- Appeals
- Tickets
- Audit log

Required template capabilities:
- Standardized reason text.
- Optional severity/weight.
- Escalation rules (example: threshold behavior like "3 strikes => ban").
- Action pipeline definition (ordered actions to run when case is created).
- Optional DM rules and message templates.

### 3) Action engine (modular automation)
Every action type is a module behind a shared contract.

Minimum initial action set:
- `record_warning`
- `send_dm`
- `timeout_user`
- `kick_user`
- `ban_user`
- `write_mod_log`

Engine requirements:
- Deterministic execution order.
- Per-action success/failure recording.
- Idempotency protection (same action cannot execute twice accidentally).
- Retry policy for transient failures.
- Safe handling for irreversible actions.

### 4) Discord integration surface
Keep Discord focused and minimal.

Required command surface:
- `/case add` with template autocomplete.
- Limited setup/discovery commands that link to web UI.
- Context-aware permission checks based on guild role mapping.

Commands to de-emphasize/remove from primary flow:
- direct punishment commands (`/ban`, `/kick`, `/timeout add`, etc.)

### 5) Web UI product surface
Web UI must be first-class for admins and staff.

Required views:
- Case template management (create/edit/archive/test).
- Case history timeline + user moderation profile.
- Staff activity and moderation statistics.
- Ticket queue and ticket logs.
- Ban appeals queue and decisions.
- Guild moderation settings and integrations.

Required UX behavior:
- Fast search/filter across users/cases/templates.
- Full audit trail visibility.
- Clear action outcome status for every automation step.

### 6) Authentication and authorization
- Discord OAuth-based identity.
- Guild-scoped RBAC (owner/admin/mod/staff roles).
- API middleware enforcing permission matrix by route + action.
- Audit log entries for privileged actions in API and UI.

### 7) Data and storage requirements
- Dedicated v5 schema (do not entangle with legacy assumptions).
- Migration files for all v5 tables/indexes/constraints.
- Soft-delete/archive strategy where appropriate (templates, cases notes).
- Indexed fields for case lookup, user lookup, and analytics queries.

### 8) Reliability and observability
- Structured logs across API, Discord adapter, and action executor.
- Correlation IDs per case request and action chain.
- Error reporting instrumentation.
- Operational health checks for DB/Redis/Discord connectivity.
- Metrics for action success/failure rates and command/API latency.

### 9) Migration and coexistence strategy
- v4 remains deployable as separate bot.
- v5 must run independently without relying on v4 runtime behavior.
- Explicit migration policy for historical data:
  - what is migrated
  - what is left behind
  - how imported data is marked
- Feature flags / guild-level rollout controls.

### 10) Testing and quality gates
Required test coverage areas:
- Template evaluation and escalation logic.
- Action engine execution semantics and idempotency.
- API authorization and permission boundaries.
- Discord command integration for `/case add` path.
- Regression tests for case creation and audit logging.

Stick to TDD practices, but don't be afraid to break the rules for the sake of progress.

Required release gates:
- Schema migrations apply cleanly on empty and existing environments.
- Critical API routes have integration tests.
- Failure scenarios are observable and recoverable.

## What is still missing (explicit backlog)

### Core platform
- Complete v5 schema + migrations.
- Repository/service layer for templates/cases/actions/audit.
- Production-ready API routes for templates, cases, users, staff, appeals, tickets.

### Moderation engine
- Template evaluator and escalation calculator.
- Action executor with retries and idempotency keys.
- Action result persistence and timeline integration.

### Discord
- `/case add` end-to-end implementation.
- Template autocomplete powered by guild templates.
- Command-level RBAC tied to API permission model.

### Web (Separate repository)
- Initial admin/staff interface for templates and case history.
- Appeals and tickets management interfaces.
- Staff analytics views.

### Ops
- Centralized audit log model.
- Structured metrics and dashboards.
- Deployment/runbook docs for v4 and v5 coexistence.

## Definition of done for v5 foundation

Quack v5 foundation is complete when:
- Moderators can execute moderation through `/case add [template]` only.
- Templates fully define reason, policy, and automation behavior.
- Action engine executes and records outcomes reliably.
- Admin/staff can manage and review moderation via web UI.
- API is the sole business-logic authority for both web and Discord surfaces.
- v4 can remain active separately without blocking v5 operation.

## Non-goals for foundation scope

- Recreating every v4 command as-is in v5.
- Building advanced customization before the template/action core is stable.
- Mixing v4 and v5 runtime logic in the same command-first architecture.
