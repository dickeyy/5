# Quack v5

Quack v5 is a configurable moderation policy and execution engine for Discord servers.

The central rule is simple:

> Guild admins define policy. Moderators invoke policy. Quack applies it consistently and records what happened.

Quack should not decide what good moderation looks like for a server. It should give admins the tools to define their own moderation workflows, then make those workflows easy for moderators to use without manually checking history, choosing escalation levels, or remembering punishment ladders.

## Product Goal

Quack v5 exists because v4 made too much moderation behavior depend on Discord commands and moderator judgment at execution time.

The v5 goal is to move policy decisions into guild configuration:

- Admins configure templates, escalation levels, actions, appeal options, and later ticket behavior.
- Moderators select the correct template when they see a rule violation.
- Quack checks the target user's history for that template.
- Quack picks the matching escalation level from the selected template.
- Quack executes the admin-defined actions for that level.
- Cases, actions, and audit entries record what happened.

This removes work from moderators. Moderators should not need to manually inspect history and decide that a third spam offense deserves a timeout. The admin already defined that rule. Quack should apply it.

## Roles

### Admins

Admins are policy makers.

They configure how their server handles moderation. In the dashboard they should eventually manage:

- Templates.
- Escalation levels.
- Actions for each level.
- Appeal options.
- Ticket settings.
- Guild-wide logging and notification settings.
- Bot customization.

### Moderators

Moderators are policy executors.

They should be able to work mostly from Discord if they want. Their main job is to identify which template applies to the situation and target the correct user.

Moderators should not:

- Choose escalation levels manually.
- Decide which punishment applies at each repeat offense.
- Recreate policy decisions each time they create a case.
- Need to move to the dashboard for every moderation action.

### Members

Members are policy targets and dashboard participants.

Members should eventually be able to use the dashboard to view their moderation data, cases, appeals, and tickets. Private staff-only comments can exist later, but the default assumption is that a user can see the moderation actions that were applied to them.

## Product Primitives

### Guild Configuration

Guild configuration is the source of truth for Quack behavior.

The bot should read guild configuration and execute it. It should avoid hardcoded moderation philosophy wherever possible.

Examples of guild-owned configuration:

- Case templates.
- Template escalation levels.
- Action definitions.
- Appeal settings.
- Ticket settings.
- Dashboard customization.
- Discord mod-log mirroring settings.

### Permissions

Discord permissions are the source of truth.

Quack should not maintain a separate staff permission system for core moderation access. Discord already has a role and permission model, and Quack should read from it.

Current intended permission model:

- Admin: user is the Discord server owner or has Discord `Administrator`.
- Moderator: user has Discord `Moderate Members`.
- Member: normal guild member without moderator/admin permission.

Quack should treat Discord server owner and Discord `Administrator` as the same admin role. Discord keeps a few owner-only powers such as deleting the server, but Quack does not need an owner-only foundation role.

Out of scope for now:

- Quack-specific permission policies.
- Quack-specific staff disabling.
- Per-template usage restrictions.
- Per-action permission gates.

Those may become future advanced features, but they should not be part of the foundation. The foundation should trust Discord permission bits.

### Templates

A template is the moderation policy for one kind of infraction or moderation workflow.

Examples:

- `no-images-in-general`
- `spam`
- `harassment`
- `slur-usage`
- `advertising`

A template is not just a saved reason. It is the instruction set that tells Quack what to do when that kind of moderation case is created.

A template owns:

- Display name.
- Slug.
- Description.
- Moderator/user-facing reason text.
- Whether the resulting case can be appealed.
- Context fields or prompts the moderator should provide.
- Escalation levels.
- Actions for each escalation level.

Every case must come from a template. Staff should not create moderation cases without a template.

### Escalation Levels

Escalation levels live inside a template.

Quack should not escalate by switching from one template to another. A moderator invokes one template, and Quack evaluates the escalation levels inside that same template.

Correct model:

```text
Template: no-images-in-general

Default level:
  Applies when no higher level matches.
  Actions:
    - record_warning

Level 2:
  Applies when this case makes 4 matching cases in the last 30 days.
  Actions:
    - record_warning
    - timeout_user notify_user=true notification_type=timeout

Level 3:
  Applies when this case makes 10 matching cases in the last 90 days.
  Actions:
    - record_warning
    - ban_user notify_user=true notification_type=ban
```

The default level is the fallback action set. The dashboard may label it "Default" or "Level 1", but implementation should treat it as the no-threshold level.

Level labels are presentation/order, not the threshold itself. It is valid for level 2 to require 5 total matching cases and level 3 to require 10 total matching cases. That is not a gap in levels; it is just the admin choosing different thresholds for each level.

Escalation evaluation:

1. Staff invokes a template for a target user.
2. Quack counts prior non-voided cases for that same target user and same template identity, across template versions.
3. Quack includes the new case in the count when evaluating thresholds.
4. Quack only evaluates the selected template's own escalation levels.
5. Quack chooses the highest matching configured level.
6. If no threshold level matches, Quack uses the template's default level.
7. Quack snapshots the selected level and actions into the case.

The phrase "highest matching level" does not mean Quack is making a policy decision. It means threshold math can make more than one level technically eligible. For example, if level 2 is `4 cases` and level 3 is `10 cases`, a user with 10 cases also meets the level 2 threshold. The deterministic rule is to apply the highest configured matching threshold.

Escalation rules should be based on case count only for now. Weight should not be part of the foundation because it is harder for normal users to understand and adds policy ambiguity.

Each escalation level can have its own time window:

- No window means all time.
- A 30-day window means count matching cases in the last 30 days.
- A 90-day window means count matching cases in the last 90 days.

Voided cases do not count toward escalation. Action failures do not automatically remove a case from escalation history; if the case should not count, it should be voided. Disabled or archived templates cannot be invoked, but cases created from them still exist historically.

### Cases

A case is the record that a moderation template was invoked against a user.

A case is not the policy. The template is the policy. A case records that the policy was applied.

A case should store:

- Guild.
- Target Discord user.
- Moderator Discord user.
- Template ID and template version.
- Selected escalation level.
- Reason.
- Context supplied by the moderator or derived from Discord.
- Link to source message/channel when available.
- Actions Quack queued or executed.
- Timeline/events.
- Whether the case is voided.
- Whether the case is appealable.

Cases are not hard-deleted. If a case should stop contributing to a user's history, it is marked void. Voided cases remain in the system for audit/history, but they do not count toward escalation.

Users should eventually be able to view their own case data in the dashboard. Private staff-only notes may exist later, but public notes are not a foundation requirement. The moderator reason is the user-facing explanation.

### Actions

Actions are generic reusable execution modules.

Admins compose actions inside template escalation levels. Quack executes the actions for the selected level.

Examples of action modules:

- Record a warning.
- Timeout a user.
- Remove a timeout from a user.
- Kick a user.
- Ban a user.

User notification is a flag on the moderation action, not a separate action. This keeps the action list aligned with what happened to the user while still letting admins choose whether the user should receive a DM.

Actions should stay generic. Quack does not need hardcoded concepts like "silent warning" or "loud warning." Those are template configurations:

```text
Silent warning:
  - record_warning

Loud warning:
  - record_warning notify_user=true notification_type=warning

Timeout with notification:
  - record_warning
  - timeout_user notify_user=true notification_type=timeout
```

Each action should define:

- Type.
- Configuration.
- Whether it should notify the user.
- Notification type, when notification is enabled.
- Execution order.
- Whether later actions continue if it fails.
- Retry behavior where applicable.
- Result recording.

Moderator-supplied content should be limited to case context and optional reason overrides where the template allows it. User-facing DMs should be determined by template/admin configuration, not improvised by moderators at execution time.

### Audit Log

The audit log is immutable and staff-only.

Everything Quack does should create audit data:

- Staff creates a case.
- Staff edits or voids a case.
- Quack executes an action.
- Quack fails to execute an action.
- Admin changes a template.
- Admin changes guild settings.

The audit log is the complete backend record. A Discord mod-log channel is a later guild-level mirror of the audit/case stream, not a per-template action. The current idea of `write_mod_log` as a template action should be reworked out of the foundation.

### User Notifications

DMs are user notifications attached to actions, not standalone template actions and not audit logs.

Admins decide whether a template action sends a DM by toggling `notify_user` on that action. The action stores a `notification_type`, such as `warning`, `timeout`, `kick`, or `ban`, so the user-facing message matches the moderation action. If no selected action has `notify_user`, Quack does not notify the user directly through DM.

DMs should eventually link to the user's case page in the dashboard.

### Discord Surface

Discord remains the fast moderation surface.

Long-term, `/case add` is the main staff command for creating moderation cases. More commands will exist later for case lookup, tickets, appeals, and other workflows.

For `/case add`:

- Moderator selects a template.
- Moderator selects a target user.
- Moderator may provide context or a reason override if the template supports it.
- Moderator never selects escalation level.
- Quack evaluates escalation automatically from the selected template and target user's matching case history.
- The command response should be public in Discord, not ephemeral, so other moderators can reference it quickly.
- Template autocomplete should show template name and a short description.

Discord command handlers should stay thin. They translate Discord interactions into application service calls. Moderation behavior belongs in services and guild configuration.

### Dashboard Surface

The dashboard is where customization and data review happen.

The dashboard should support different audiences:

- Admins configure templates, escalation levels, actions, appeal settings, tickets, and guild settings.
- Moderators can issue cases, handle appeals, handle tickets, and inspect moderation history.
- Members can view their moderation data and interact with appeals/tickets.

The dashboard should be the best place to build and review policy. Discord should be the fastest place to execute policy.

This backend repo should expose clean APIs for the dashboard, but the dashboard itself lives in a separate repo.

### Appeals

Appeals are a later module, but the product model should be clear now.

An appeal is attached to a case. Templates can decide whether cases created from them are appealable.

Appeal forms should be customizable per guild/template. Quack can provide defaults, but admins should be able to edit them.

Appeals are not actions. They are a workflow where a member asks staff to review a case.

### Tickets

Tickets are a later module and separate from appeals.

A ticket is a private support/moderation conversation between a member and staff. It is not a moderation action and does not belong in the action pipeline.

Tickets should eventually be customizable, but they should not block the core template/case/action foundation.

- Discord command registry and hash-based command sync.
- Discord `/case add` with template autocomplete and case creation.

Known implementation drift:

- Guild access now derives foundation roles and action permissions from Discord permission bits. Legacy permission-policy and disabled-staff columns may still exist in the schema, but they should not gate foundation access.
- Template creation and case creation now use the corrected level model, but legacy flat action/rule columns may still exist physically until a cleanup migration removes them.
- The current `write_mod_log` action treats Discord mod-log posting as a template action. Mod-log mirroring should become a guild-level logging setting later.
- The current `/case add` response is too private/ephemeral for the desired Discord workflow. It should become a public moderation reference response.

## Correct Case Creation Flow

The desired backend flow is:

1. Receive case creation request from Discord or dashboard.
2. Resolve guild and actor from Discord permission bits.
3. Require the actor to be admin or moderator.
4. Load the selected template.
5. Reject disabled or archived templates.
6. Validate required context/reason fields.
7. Count prior non-voided cases for the same target user and same template.
8. Include the new case in the threshold count.
9. Select the highest matching escalation level, or the default level if none match.
10. Create the case.
11. Snapshot template version, selected level, reason, context, and actions.
12. Create initial case timeline event.
13. Create action execution rows for the selected level's actions.
14. Write audit entry.
15. Queue action execution.
16. Return a response that clearly states the case number, template, selected level, and queued actions.

## Implementation Principles

### Keep Quack configurable

If behavior can reasonably be admin-defined, prefer making it configuration instead of hardcoding moderation philosophy.

### Use Discord permissions

Discord is the source of truth for admin/moderator status. Do not build a competing staff permission system in the foundation.

### Keep routes and commands thin

Routes and Discord handlers translate requests. Services apply product behavior. Storage persists state.

### Snapshot history

Cases must preserve what happened at the time. Editing a template later should not rewrite old cases.

### Build vertically

Each slice should end in a usable path. Avoid broad scaffolds that do not produce a working moderation workflow.
